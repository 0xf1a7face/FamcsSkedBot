# Сохранение цветовых отметок

База: `schedule_db`, binding `DB`, таблица `miniapp_colors`. Строка выбирается по
`telegram_id` из проверенного Telegram `initData`. Поле `colors_json` содержит весь
документ `{ schemaVersion, savedAt, colors, recentColors }`, `revision` защищает от
перезаписи устаревшим документом. Расписание остаётся в KV.

Ключ новой отметки — JSON-массив:
`["lesson-v3","математический анализ",["иванов"]]`.
Совпадение названия пары и фамилии преподавателя даёт одну цветовую отметку во всех
группах, подгруппах, курсах и режимах просмотра. Другой предмет или другая фамилия
дают независимую отметку. Регистр, пробелы, ё/е нормализуются; инициалы и должность
преподавателя не входят в ключ. Для нескольких преподавателей используется
отсортированный набор фамилий. Без названия или фамилии ключ не создаётся.

Старые ключи без фамилии сохраняются в JSON, но не используются для отображения:
определить преподавателя по старому формату невозможно. Исходный `lessonColors:v1`
также сохраняется. Для восстановления нужно явное сопоставление предмета и фамилии;
текущее расписание само по себе не доказывает принадлежность старой отметки.

Клиент немедленно записывает изменения и удаления в `colors:account:<id>` на
устройстве. Через 3 секунды после последней правки отправляет один полный JSON.
Первое открытие требует GET; последующие записи используют полученную ревизию без
дополнительного GET. При 409 клиент перечитывает серверный документ и накладывает
только неподтверждённые изменения. При сетевой ошибке сохраняет очередь и повторяет
запрос с увеличивающейся задержкой. Новые правки не удаляются поздним подтверждением.

Обновление видимой страницы — раз в 10 минут, при возврате в приложение — если
последнее чтение было больше минуты назад. Скрытие страницы инициирует отправку
очереди; небольшой запрос использует `keepalive`. Это не гарантирует завершение
запроса при принудительном закрытии WebView, поэтому очередь остаётся на устройстве
до подтверждения. Документы ограничены 2000 отметками, ключом в 512 символов и
телом запроса в 1 000 000 байт.

## Настройка и проверка

Из `pkgs/worker-api`, перед публикацией API:

```powershell
npx.cmd wrangler d1 migrations apply schedule_db --remote
```

Миграция `0001_miniapp_colors.sql` создаёт отсутствующую таблицу и не удаляет
имеющиеся записи. Нужен также секрет `TELEGRAM_BOT_TOKEN` того бота, через которого
открывается Mini App. Проверять сохранение надо в Telegram: обычная вкладка сайта
без `initData` сохраняет только локальные гостевые отметки.

Диагностика структуры (не раскрывает пользовательские цвета):

```sql
PRAGMA table_info(miniapp_colors);
SELECT COUNT(*) AS documents, MAX(revision) AS max_revision FROM miniapp_colors;
```

Локальные проверки: `node --test tests/colors.test.mjs`, `npx.cmd tsc --noEmit`;
для клиента — `node --test tests/*.test.mjs` из `pkgs/frontend`.

Обоснование хранения: D1 поддерживает [JSON в TEXT](https://developers.cloudflare.com/d1/sql-api/query-json/),
учитывает [прочитанные и записанные строки](https://developers.cloudflare.com/d1/platform/pricing/).
Поиск по первичному ключу пользователя не требует сканировать всю таблицу.
